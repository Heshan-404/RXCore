Implement secure administrator authentication and dashboard-managed selective WARP domain routing in this Rust VPN core.

Environment:

- Rust
- Axum administration dashboard
- Tokio current-thread runtime
- 1 vCPU
- 2 GB RAM
- VLESS Reality
- Hysteria/UDP
- WARP selective routing
- Cached pre-serialized dashboard responses
- Existing subscription pages that generate Smart, Browsing WARP, and Low Latency profiles

Primary requirements:

1. The main dashboard at `/` must require an administrator password.
2. Subscription pages must not require the administrator password.
3. Subscription pages remain protected by secure subscription tokens.
4. On the first interactive server run, securely request and confirm the administrator password.
5. On later runs, display a login page when the dashboard is opened.
6. Add an authenticated dashboard button to change the administrator password.
7. Add WARP domain management to the main dashboard.
8. Global WARP domain rules should apply to all accounts using Smart Selective mode.
9. Browsing WARP mode should use WARP by default and support global Direct Exceptions.
10. Authentication and routing management must not increase established VPN ping, jitter, or forwarding CPU usage.

Do not add authentication checks, route-table lookups, password operations, JSON serialization, filesystem operations, or dashboard state access inside packet-forwarding loops.

==================================================
1. FIRST-RUN ADMIN INITIALIZATION
==================================================

Do not request a password during `cargo build`.

Builds must always remain non-interactive.

Request the password only when the server binary runs and no administrator credential exists.

Store administrator credentials separately from `config.json`.

Suggested path:

data/admin_credentials.json

The credential file must contain only:

- Argon2id password hash in PHC format
- session signing secret
- session epoch
- created timestamp
- updated timestamp
- password algorithm version

Example structure:

struct AdminCredentials {
    password_hash: String,
    session_secret: String,
    session_epoch: u64,
    created_at: i64,
    updated_at: i64,
    version: u32,
}

Never store:

- plaintext administrator password
- reversible encrypted password
- password inside config.json
- password inside logs
- password inside environment diagnostics
- password inside dashboard JSON
- password inside browser localStorage

==================================================
2. INTERACTIVE FIRST RUN
==================================================

When the credential file does not exist and stdin is an interactive terminal:

Display:

Ruve VPN Administrator Setup
Create a password for the administration dashboard.

Prompt:

Administrator password:
Confirm administrator password:

Hide terminal input while typing.

Validation:

- minimum 12 characters
- maximum 128 characters
- reject empty or whitespace-only values
- reject mismatched confirmation
- allow password managers and passphrases
- do not require arbitrary character-class rules

After successful entry:

1. Generate a cryptographically secure random salt.
2. Hash using Argon2id.
3. Generate a separate random 32-byte session-signing secret.
4. Write the credential file using:
   - temporary file
   - fsync
   - atomic rename
5. Set Linux permissions to `0600`.
6. Never print the password or complete credential file.
7. Continue normal server startup.

Use a suitable password-input crate that disables terminal echo, such as `rpassword`, or an equivalent secure implementation.

==================================================
3. NON-INTERACTIVE FIRST RUN
==================================================

A systemd service normally has no interactive terminal.

When credentials are missing and stdin is not interactive:

- do not start the administration dashboard without authentication
- do not create a default password
- do not generate and print a permanent password
- do not temporarily expose an unauthenticated setup page
- fail closed with a clear error

Display:

Administrator credentials are not initialized.

Run:

target_core admin init

or:

target_core admin set-password

Add CLI commands:

target_core admin init
target_core admin set-password
target_core admin reset-password

Behavior:

admin init:
- allowed only when no credential file exists
- prompts securely for a new password

admin set-password:
- requires the current administrator password when credentials exist
- prompts securely for a replacement password

admin reset-password:
- intended for a server administrator with filesystem/root access
- must require an explicit confirmation flag
- must not expose the old password
- rotates the password hash
- rotates the session signing secret
- increments the session epoch
- invalidates every active dashboard session

Support secure automated initialization using a password file:

target_core admin init --password-file /secure/path/admin-password

Requirements:

- file must not be world-readable
- read once
- do not log file contents
- do not accept plaintext passwords directly as command-line arguments
- command-line arguments may be visible to other processes

==================================================
4. PASSWORD HASHING
==================================================

Use Argon2id.

Recommended initial parameters for this 1-vCPU, 2-GB VPS:

- memory: 32 MiB
- iterations: 2
- parallelism: 1

Make parameters versioned and configurable within safe bounds.

Do not perform Argon2 work on the Tokio current-thread reactor.

Use:

- a dedicated administrator-auth semaphore with capacity 1
- `tokio::task::spawn_blocking`
- no state lock held while awaiting verification

Example control:

admin_auth_cpu: Semaphore::new(1)

Argon2 operations occur only during:

- login
- password change
- CLI initialization/reset

Do not verify the password on every dashboard request.

Benchmark the selected parameters on the VPS.

Target:

- strong password hashing
- reasonable login time
- no extended one-core CPU spike

Do not silently downgrade to plaintext, SHA-256-only, MD5, or unsalted hashes.

6. ADMIN AUTHENTICATION ENDPOINTS
==================================================

Add:

POST /api/auth/login
POST /api/auth/logout
GET  /api/auth/session
POST /api/auth/change-password

POST /api/auth/login

Request:

{
  "password": "..."
}

On success:

- issue a secure authenticated session cookie
- return a minimal success response
- do not return the session secret in JSON

On failure:

- return a generic 401 or 429 response
- do not log the submitted password
- do not reveal hash timing information beyond normal secure verification

POST /api/auth/logout

- clear the session cookie
- require CSRF protection
- return success even when the session is already invalid

GET /api/auth/session

Return only:

{
  "authenticated": true,
  "expires_at": 1234567890
}

Do not include credential hashes or session secrets.

POST /api/auth/change-password

Request:

{
  "current_password": "...",
  "new_password": "...",
  "confirm_password": "..."
}

Requirements:

1. Require a valid administrator session.
2. Require CSRF protection.
3. Verify the current password using Argon2id.
4. Validate the new password.
5. Ensure confirmation matches.
6. Generate a new salt.
7. Generate the new Argon2id hash.
8. Increment `session_epoch`.
9. Optionally rotate the session-signing secret.
10. Atomically persist the credential file.
11. Invalidate all previous sessions.
12. Issue a new session for the current administrator or require immediate re-login.
13. Never log either password.

Preferred behavior:

- invalidate every previous session
- issue one fresh session to the administrator who changed the password
- log out other browsers/devices

==================================================
7. SESSION DESIGN
==================================================

Use a lightweight signed session cookie.

Do not store a large server-side session HashMap for ordinary use.

Suggested session claims:

struct AdminSessionClaims {
    issued_at: i64,
    expires_at: i64,
    session_epoch: u64,
    csrf_token: [u8; 32],
}

Encode the claims and authenticate them using:

HMAC-SHA256

Use the random session secret stored in the administrator credential file.

Cookie requirements:

- HttpOnly
- SameSite=Strict
- Path=/
- short clear name, such as `ruve_admin_session`
- maximum age approximately 12 hours
- Secure when using HTTPS

When the management interface is accessed through plain HTTP:

- allow a non-Secure cookie only when the API is bound to loopback
- warn and refuse public non-TLS administration
- never serve password authentication publicly over plaintext HTTP

Validate on every protected HTTP request:

- HMAC
- expiry
- session epoch
- cookie format

This should require only:

- cookie parsing
- HMAC verification
- atomic credential/session-epoch read

Do not run Argon2id on every request.

==================================================
8. CSRF PROTECTION
==================================================

All state-changing administrator requests must require CSRF validation.

Protected methods:

- POST
- PUT
- PATCH
- DELETE

Use a double-submit or signed-session-bound CSRF token.

One acceptable design:

- CSRF value exists inside the signed session claims
- same value is provided to the browser through a separate readable CSRF cookie
- JavaScript sends it as `X-CSRF-Token`
- middleware verifies that the header value matches the signed claim

Require CSRF protection for:

- password changes
- logout
- user creation/deletion
- Reality profile creation/deletion
- WARP domain changes
- routing changes
- WARP restart/recheck
- quota changes
- configuration changes

Do not require CSRF for read-only GET requests.

==================================================
9. LOGIN RATE LIMITING
==================================================

Add bounded login protection.

Suggested initial limits:

Per source IP:
- 5 failed attempts per 5 minutes

Global:
- 20 failed attempts per 5 minutes

After repeated failures:

- apply exponential delay
- return 429
- do not queue Argon2 jobs indefinitely

Use bounded state with expiry.

Do not store an unbounded IP map.

Normalize:

- IPv4
- IPv4-mapped IPv6
- IPv6

When the panel is behind a reverse proxy:

- trust forwarded client IP headers only from explicitly configured trusted proxies
- otherwise use the actual TCP peer address

Successful login should clear or reduce the failure counter for that source.

Use rate-limited warning logs without password data.

22. IMMUTABLE ROUTE TABLE UPDATE
==================================================

Compile domain configuration into immutable route tables.

Suggested model:

struct RouteModeTables {
    smart: Arc<CompiledRouteTable>,
    browsing_warp: Arc<CompiledRouteTable>,
    low_latency_direct: Arc<CompiledRouteTable>,
    generation: u64,
}

Publish using:

ArcSwap<RouteModeTables>

When an administrator changes a domain set:

1. Authenticate the request.
2. Validate CSRF.
3. Validate and normalize the domains.
4. Create a staged configuration update.
5. Compile new route tables outside state locks.
6. Use bounded `spawn_blocking` only when compilation is CPU-heavy.
7. Publish the completed route tables atomically.
8. Persist through the existing ordered persistence worker.
9. Do not restart the VPN process.
10. Do not restart Reality listeners.
11. Do not restart WARP.
12. Do not disconnect existing sessions.

At connection setup:

1. Determine the selected profile mode.
2. Load the route-table Arc once.
3. Resolve the destination route once.
4. Store the selected outbound in the connection context.
5. Enter the existing forwarding path.

Never perform domain-rule lookup inside:

- TCP copy loops
- UDP packet loops
- quota loops
- rate limiter loops
- dashboard polling handlers

23. WARP FAILURE BEHAVIOR
==================================================

Smart mode:

- non-matching traffic remains direct
- matching WARP domains follow the configured WARP failure policy
- do not delay direct traffic while checking WARP

Browsing WARP:

- WARP by default
- Direct Exceptions remain direct
- fail fast or use explicit configured fallback when WARP is unavailable

Low Latency Direct:

- never consult WARP health
- never wait for WARP
- always direct

WARP health checks must run periodically in the control plane.

Do not run:

- warp-cli
- systemctl
- external HTTP health requests
- route commands

inside dashboard request handlers or connection hot paths.

26. PASSWORD CHANGE PERFORMANCE
==================================================

with:
